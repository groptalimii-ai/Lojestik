# FreightAI Saudi — Phase 1 MVP

نظام تشغيل أعمال لوساطة النقل البري يعمل عبر Telegram Bot، مبني على FastAPI + PostgreSQL + Anthropic API.

> ⚠️ **Disclaimer / إخلاء مسؤولية:** هذا النظام أداة لتنظيم ومطابقة طلبات النقل ولا يغني عن التراخيص أو المتطلبات النظامية ذات الصلة. This system is a tool for organizing and matching freight requests; it does not replace required licenses or regulatory compliance.

## ما تم إنجازه في هذه المرحلة (Phase 1)

- ✅ Telegram Bot (aiogram 3) بواجهة عربية: `/start`, `/help`, `/newload`, `/registercarrier`, `/mytrucks`, `/support`
- ✅ استخراج بيانات الحمولة من نص حر (عربي/إنجليزي/لهجات) عبر Anthropic API
- ✅ رحلة الناقل كاملة: تسجيل الناقل → إضافة شاحنة خطوة بخطوة (نوع الرأس، المقطورة، الحمولة القصوى، الموقع، الخطوط، التوفر، السعر، حمولة العودة) → عرض الشاحنات المسجّلة عبر `/mytrucks`
- ✅ قاعدة بيانات PostgreSQL كاملة (users, companies, carriers, trucks, loads, matches, quotes, deals, payments, fraud_flags, audit_logs)
- ✅ محرك مطابقة (Matching Engine) قائم على قواعد واضحة وقابلة للتدقيق (0-100 + أسباب)
- ✅ محرك مالي يفصل الإيراد عن الربح (Gross margin, Margin %, Net profit)
- ✅ آلة حالات للصفقة (Deal Lifecycle) تمنع تجاوز المراحل بدون صلاحية Admin
- ✅ REST API كامل (FastAPI + OpenAPI تلقائي على `/docs`)
- ✅ Docker Compose للتشغيل المحلي بأمر واحد
- ✅ Unit tests لمحرك المطابقة والمحرك المالي
- ✅ حد يومي للطلبات لكل حساب (Rate Limiting) عبر Redis — منفصل لكل خدمة (استخراج AI، إنشاء حمولة، إجراءات الناقل)

## Architecture

```
Telegram User → aiogram Bot → FastAPI Backend → PostgreSQL
                                    ↓
                          Anthropic API (extraction only)
                                    ↓
                    Matching Engine (rule-based) + Financial Engine
```

## Installation / التشغيل

1. انسخ ملف البيئة:
   ```bash
   cp .env.example .env
   ```
2. عبّئ القيم في `.env`:
   - `TELEGRAM_BOT_TOKEN` من [@BotFather](https://t.me/BotFather)
   - `ANTHROPIC_API_KEY` من console.anthropic.com
   - غيّر `POSTGRES_PASSWORD` و `JWT_SECRET` عن القيم الافتراضية
3. شغّل المشروع:
   ```bash
   docker compose up --build
   ```
4. الـ API متاح على: `http://localhost:8000/docs`
5. البوت سيبدأ Polling تلقائيًا بمجرد صحة التوكن.

## قناة الإدخال اليدوي (Manual Intake Channel)

بدل انتظار تسجيل ذاتي كامل من كل ناقل أو صاحب حمولة، يمكن للمشغّل (admin) لصق رسائل نصية حرة مباشرة في محادثته الخاصة مع البوت (`TELEGRAM_ADMIN_CHAT_ID`)، والبوت يصنّفها ويخزّنها تلقائيًا:

```
ابو سعد سطحه من الدمام للرياض رقم التواصل 05xxxxxxxx
→ 🚚 ناقل: يُخزَّن في carrier_leads

خالد حمولة 29 طن من الرياض لجدة السعر 3000 رقم التواصل 05xxxxxxxx
→ 📦 صاحب حمولة: يُخزَّن في load_leads + companies
```

**قاعدة التصنيف** (`backend/app/services/lead_extraction.py::classify_intake_text`): أي رسالة تحتوي "حمولة" أو "طن" → صاحب حمولة، غير ذلك → ناقل. هذه قاعدة كلمات مفتاحية بسيطة (ليست AI) لأنها قاعدة المشغّل نفسه بدقة كاملة لأسلوب كتابته. الـ AI يُستخدم فقط بعد التصنيف لاستخراج الحقول (الاسم، الجوال، نوع الشاحنة، المسار، الوزن، السعر).

**التفعيل مطلوب يدويًا مرة واحدة**: لا يوجد API لترقية حساب لـ admin (نقطة تصعيد صلاحيات خطيرة لو كانت متاحة عبر API)، لذا شغّل مرة واحدة بعد أول رسالة ترسلها للبوت:
```bash
python scripts/promote_admin.py <telegram_id>
```

## تحسينات "الذكاء بدل التكلفة" (Zero-Cost Intelligence)

ثلاث إضافات عملية تستخدم بيانات وحسابات مجانية بدل خدمات مدفوعة، بما ينسجم مع مبدأ Zero-Cost Bootstrapping الأساسي للمشروع:

1. **كاش استخراج AI** (`backend/app/services/ai_cache.py`) — كاش مطابقة نصية دقيقة (exact-match، مو fuzzy/semantic) عبر Redis لمدة 7 أيام. يوفّر استدعاءات Claude المكررة (رسالة مُعاد إرسالها/لصقها بنفس النص حرفيًا)، وهذا شائع فعليًا في قناة الإدخال اليدوي. **صراحة: هذا Cache بسيط بالـ hash، وليس "AI ذكي" — أي اختلاف بسيط بالنص (غير المسافات) يعتبر رسالة جديدة.**
2. **تقدير المسافة مجانًا** (`backend/app/services/geo.py`) — جدول إحداثيات ثابت لأهم مدن السعودية والخليج + معادلة Haversine، بدل أي API خرائط مدفوع. يملأ تلقائيًا `locations.latitude/longitude` و`trip_records.distance_km` (كانا مصمَّمين بالجدول من البداية بدون مصدر بيانات فعلي). **قيد صريح: مسافة خط مستقيم، وليست مسافة طريق فعلية — تقريب معقول للمسارات بين المدن الكبرى، غير دقيق لمسارات فيها التفافات كبيرة.**
3. **اقتراح سعر إحصائي** (`backend/app/services/pricing_engine.py`) — Median على الأسعار الفعلية المتوفرة حاليًا (`load_leads.price` من قناة الإدخال اليدوي)، مع الانتقال التلقائي لـ `trip_records.final_accepted_price` (صفقات مُغلقة فعليًا) بمجرد توفرها لاحقًا. **قيد صريح: هذا Median بسيط، وليس نموذج ML مدرَّب — بحجم البيانات الحالي، نموذج مدرَّب سيتعلم ضوضاء لا نمط حقيقي، فيعطي ثقة زائفة. يظهر للسائق حجم العينة ومستوى الثقة (منخفض/متوسط) بصراحة بدل رقم بلا سياق.**

## قاعدة بيانات النقلات الموحّدة + التطابق التلقائي

**رقم الهاتف كمفتاح هوية حقيقي** (`backend/app/services/phone_normalizer.py`): كل الأرقام تُطبَّع لصيغة موحدة (`966501234567`) بغض النظر عن طريقة كتابتها (`0501234567` / `+966 50 123 4567` / `00966501234567`...)، بدل مطابقة نصية حرفية كانت تُنشئ سجلًا مكررًا لنفس الشخص بأي اختلاف كتابة بسيط. هذا هو الأساس اللي بنيت عليه الميزتين التاليتين.

**إشعار تطابق تلقائي**: كل رسالة جديدة (حمولة أو ناقل) تُقارَن فورًا بالجدول المقابل على نفس المسار بالضبط (`origin_location_id` + `destination_location_id`)، وأول ٥ تطابقات تُعرض لك مباشرة في رد البوت — بدون ما تراجع القوائم يدويًا.

**نشاط الناقل (وليس "تقييم موثوقية")** — تنبيه صريح مهم: جدول `carrier_profiles` الجديد يتتبّع **كم مرة تكرر ذكر نفس رقم الهاتف** فقط، مو موثوقية أو أداء فعلي. ليش؟ لأنه ما عندنا حاليًا أي بيانات عن نتيجة فعلية (هل التسليم تم؟ هل صار تأخير أو مشكلة؟) — وهذي البيانات تحتاج مسار "إغلاق صفقة" غير موجود بعد بالمشروع. سميتها بصراحة "نشاط" مو "تقييم" لأن تسميتها تقييم موثوقية وهي مجرد عداد تكرار = معلومة مضللة، والمضلِّل أخطر من غيابه. بمجرد ما يوجد مسار إغلاق صفقات فعلي، هذا نفس الجدول اللي راح تتجمّع فيه بيانات الموثوقية الحقيقية.

## Google Maps Integration (مُجمّدة حتى الإطلاق التجاري)

الكود موجود وجاهز بالكامل، لكنه **no-op تمامًا افتراضيًا** — صفر استدعاءات لـ Google، بغض النظر عن أي إعداد آخر، إلا لو الشرطين التاليين تحققا معًا:

```bash
GOOGLE_MAPS_ENABLED=true
GOOGLE_MAPS_API_KEY=<مفتاحك>
```

**كيف تشتغل الآلية (`backend/app/services/geo.py` + `google_maps_client.py`):**
- **الجدول الثابت المجاني يبقى المصدر الأساسي دائمًا.** Google Maps يُستدعى فقط في حالتين: (1) مدينة مو موجودة بالجدول الثابت (Geocoding)، أو (2) عند حساب مسافة طريق فعلية بدل خط مستقيم (Distance Matrix) — وحتى في هذي الحالة، فقط لو الإحداثيات الاثنين معروفة أصلًا.
- **كل إحداثيات مدينة تُحفَظ بجدول `locations` عند أول استخدام** — يعني حتى بعد التفعيل، أي مدينة تكرر ذكرها ما تستدعي Google مرة ثانية أبدًا. هذا يقلل التكلفة الفعلية بشكل كبير جدًا مقارنة باستدعاء API كل مرة.
- **لو صار خطأ بالـ API أو انقطع الاتصال، يرجع تلقائيًا للحساب المجاني (Haversine)** — الميزة ما تتعطل أبدًا، بس تفقد دقة الطريق الفعلي مؤقتًا.

**قبل ما تفعّلها فعليًا عند الإطلاق التجاري، اعرف التكلفة الحقيقية:**
- تحتاج حساب Google Cloud Platform مع بطاقة ائتمان مربوطة (حتى ضمن الرصيد المجاني الشهري)
- Geocoding API وDistance Matrix API لهما تسعير لكل طلب بعد الرصيد المجاني — راجع [أسعار Google Maps Platform الحالية](https://mapsplatform.google.com/pricing/) وقت التفعيل الفعلي، لأنها تتغير
- بما أن كل مدينة تُحفَظ بعد أول resolve، التكلفة الفعلية عادة تكون منخفضة جدًا (عدد المدن الفريدة، مو عدد الرسائل)، لكن لازم تراقبها أول شهر بعد التفعيل

## الطبقة المالية (مُجمّدة حتى الإطلاق التجاري)

**على عكس Google Maps، هذا التجميد ليس "كود جاهز بانتظار مفتاح" — هو انتظار قرارات عمل/قانونية حقيقية لا علاقة لها بالكود إطلاقًا:** اختيار بوابة دفع، شراكة بنكية، اعتماد الفوترة الإلكترونية (ZATCA)، ترخيص تجاري رسمي. لا يوجد إعداد (`.env` flag) يفعّلها لأنه لا يوجد ما يُفعَّل بعد.

**الوضع الحالي بالتحديد:**
- **جدول `payments`** موجود بالمخطط (`deal_id`, `direction`, `amount`, `paid_at`, `method`) — **صفر endpoint يكتب فيه.** الشكل جاهز مسبقًا عشان العمل المستقبلي يدخل بمكانه المُصمَّم له، بدل migration طارئ يوم أول دفعة حقيقية.
- **`Deal.customer_paid` / `Deal.carrier_paid`** — تُقرأ فقط، **لا توجد أي طريقة تُحدَّث بها لـ `True`.** يعني `capital_progress()` و`completed_deals_retained_profit()` بـ `services/financial.py` **سترجع صفر دائمًا** حتى لو أُغلقت صفقات فعلية — هذا سلوك صحيح وصادق لبيانات لم تُجمَع فعليًا، وليس خطأ يحتاج "إصلاح" بتزييف الأعلام.
- **جدول `fraud_flags`** — نفس الوضع، صفر استخدام، بانتظار حجم صفقات حقيقي يستاهل كشف احتيال عليه.

**قبل تفعيل أي جزء من هذا فعليًا، يلزم (خارج نطاق الكود بالكامل):**
- اختيار بوابة دفع (مدى/بطاقات) وشراكة بنكية فعلية
- اعتماد نظام الفوترة الإلكترونية (ZATCA) — إلزامي قانونيًا لأي منشأة مسجّلة بضريبة القيمة المضافة
- سجل تجاري رسمي بنشاط مطابق (وساطة نقل)

## Rate Limiting / حد الطلبات اليومي

كل مستخدم (هويته الحقيقية عبر JWT صادر من `/auth/telegram`، وليس أي هيدر يرسله العميل) له حد يومي منفصل لكل خدمة، مخزَّن في Redis ويُعاد ضبطه تلقائيًا عند منتصف الليل UTC بدون الحاجة لـ cron job:

| الخدمة | الحد الافتراضي/يوم | متغير البيئة |
|---|---|---|
| استخراج AI (`/ai/extract-load`) | 30 | `RATE_LIMIT_AI_EXTRACT_PER_DAY` |
| إنشاء حمولة (`/loads`) | 20 | `RATE_LIMIT_LOADS_PER_DAY` |
| إجراءات الناقل (تسجيل/شاحنة) | 20 | `RATE_LIMIT_CARRIER_ACTIONS_PER_DAY` |
| طلب تسعير (`/pricing/request`) | 5 | `RATE_LIMIT_PRICING_PER_DAY` |
| القناة اليدوية (`/intake/message`) | 1000 (سقف حماية تكلفة، ليس قيدًا تشغيليًا) | `RATE_LIMIT_INTAKE_PER_DAY` |
| افتراضي لأي خدمة أخرى | 100 | `RATE_LIMIT_DEFAULT_PER_DAY` |

عند تجاوز الحد، يعيد الـ API خطأ `429` برسالة عربية واضحة، والبوت يعرضها للمستخدم مباشرة بدل رسالة خطأ عامة. المنطق في `backend/app/services/rate_limit.py`.

## Security

- لا توجد أي مفاتيح أو Tokens مكتوبة في الكود — كلها عبر `.env`
- `.env` مضاف إلى `.gitignore`
- المصادقة: مصافحة موقّعة بـ HMAC بين البوت والباك-إند (`BOT_SERVICE_SECRET`) تُصدر JWT قصير الصلاحية لكل مستخدم؛ لا توجد نقطة API واحدة (عدا `/auth/telegram` و`/health`) تعمل بدون `Authorization: Bearer` صالح
- كل حقول الهوية (shipper_id، user_id الخاص بالناقل، هوية السائق في طلبات التسعير) تُشتق من الجلسة الموثّقة على الخادم — لا تُقبل أبدًا من جسم الطلب
- صلاحيات Admin (انتقالات حالة الصفقة، لوحة التحليلات) تُقرأ من `current_user.role` في قاعدة البيانات، وليس من قيمة يرسلها العميل
- Deal status transitions محمية بآلة حالات صريحة (`app/services/deal_lifecycle.py`)
- جدول `fraud_flags` و `audit_logs` جاهزان للاستخدام في Phase 2

### مراجعة صارمة إضافية — ١٢ خطأ حقيقي، جميعها مُصلَحة
- **حرجة (كانت تسبب فشل فعلي):** `GET /carriers/by-phone/{phone}` كان يقارن الرقم الخام بالرقم المُطبَّع المخزَّن → يفشل دائمًا لكل ناقل حقيقي (كسر كامل لتدفق `/mytrucks`). `POST /loads/{id}/matches` كان ينهار (500) في كل استدعاء بسبب lazy-load غير متزامن (`truck.carrier` بدون `selectinload`).
- **مهمة:** كاش استخراج AI كان يخزّن التاريخ *بعد* حسابه، فرسالة مُعاد إرسالها بعد أيام ترجع تاريخًا خاطئًا لعبارات نسبية ("الخميس"). تحديث حالة الصفقة كان يمسح موافقة الأدمن السابقة عند أي انتقال لاحق يسويه مستخدم عادي. عدة endpoints (`carriers.py`, `deals.py`) كانت ترجع كائنات SQLAlchemy خام بدون `response_model` (خطر فشل تسلسل JSON). `DealCreate` بلا تحقق من وجود `load_id`/`truck_id`/`carrier_id`.
- **متعلقة بجودة المطابقة:** تهجئات مختلفة لنفس المدينة ("الطايف" مقابل "الطائف") كانت تُنشئ سجلّي `Location` منفصلين رغم أن `geo.py` يعرف أنهما نفس المدينة — يكسر ميزة التطابق التلقائي بصمت. أُضيفت `canonicalize_city_name()` لتوحيدها.
- **محرك المطابقة غير مستخدَم:** كان موجودًا لكن لا شيء بالبوت يستدعيه — أصبح يُعرض تلقائيًا بعد إنشاء أي حمولة.
- **صغيرة:** `database_url` بدون قيمة افتراضية كان يكسر استيراد ملفات الاختبار بدون `.env`. `settings.jwt_algorithm` معرَّف لكن غير مستخدم فعليًا. حقول UUID وهمية باقية بكود البوت من مرحلة ما قبل JWT. رسالة خطأ عامة بقناة الإدخال اليدوي كانت تقترح دائمًا "تحقق من صلاحية admin" حتى لأخطاء خادم حقيقية غير متعلقة.

### إغلاق فجوات موثوقية وأمان (بعد سؤال مباشر عن الجاهزية للتوسع)
- **`audit_logs` كان جدولًا فارغًا تمامًا** (معرَّف بقاعدة البيانات، لا شيء يكتب فيه) — أُضيفت `services/audit.py` وتُسجَّل الآن موافقات الأدمن على الصفقات وعمليات `promote_admin.py`.
- **`Load.extraction_confidence` كان يُحسَب ويُعرض للسائق لكن يضيع قبل التخزين** — أصبح يُخزَّن فعليًا، ويُعرض تحذير صريح للسائق قبل التأكيد لو كانت الثقة منخفضة (<0.6).
- **`passlib[bcrypt]` كانت dependency ميتة** (غير مستخدمة إطلاقًا — لا كلمات مرور بالنظام) — أُزيلت من `requirements.txt`.
- **لا حماية من استدعاءات AI الفاشلة مؤقتًا** — أُضيفت `services/ai_retry.py` (إعادة محاولة تلقائية بـ backoff تصاعدي لأخطاء الشبكة/الخادم المؤقتة فقط، بدون إعادة محاولة أخطاء العميل الحقيقية). كذلك: طلب فاشل فعليًا (حتى بعد المحاولات) **كان يُخصَم من حصتك اليومية بلا فائدة** — أُضيفت `refund_user_rate_limit()` لإرجاعها.
- **بيانات AI المستخرَجة بقناة الإدخال اليدوي كانت تُخزَّن بلا أي حد لطول النص** (على عكس `/newload` اللي فيها حدود صريحة) — أُضيف `_bounded()` يقصّ أي قيمة قبل التخزين، دفاع إضافي ضد نص مُحقَن أو مهلوَس طويل بشكل غير طبيعي.
- **الثقة (confidence) لم تكن موجودة إطلاقًا بقناة الإدخال اليدوي** — أُضيفت لكل من `CARRIER_LEAD_PROMPT`/`LOAD_LEAD_PROMPT`، وعمود `needs_review` جديد بجدولي `carrier_leads`/`load_leads` يُفعَّل تلقائيًا عند ثقة منخفضة، ويظهر تحذير صريح بردّ البوت.

### الحد الأقصى الحالي لرفع الجودة (بعد طلب "أقصى ما تستطيع فعله")
- **لا يوجد rotation/revocation للـ JWT** — أُغلقت فعليًا: `POST /auth/logout` يبطل توكن واحد فورًا (Redis blacklist بـ `jti`)، و`scripts/promote_admin.py` يبطل **كل** توكنات المستخدم تلقائيًا عند تغيير صلاحيته (`User.tokens_valid_after`) — بدون هذا، توكن مُخزَّن مسبقًا بالبوت (كاش لمدة ساعة) كان يبقى يقول "غير admin" لين ينتهي طبيعيًا. جانب العميل بالبوت (`api_client.py`) يتعامل مع `401` تلقائيًا (يجدّد التوكن ويعيد المحاولة مرة وحدة) بدل ما يظهر خطأ مربك للمستخدم.
- **Race condition حقيقي على `Location`/`Company`/`CarrierProfile`** — كان موثّقًا كـ "فجوة معروفة، منخفضة الأولوية". أُصلح فعليًا: قيود فريدة (`UniqueConstraint`) على مستوى قاعدة البيانات + `services/db_utils.py::get_or_create` (نمط SAVEPOINT صحيح: عند تعارض من طلب متزامن، يسحب السجل الفائز بدل الانهيار أو التكرار الصامت).
- **لا فحص ثغرات تلقائي للـ dependencies** — أُضيف `pip-audit` كـ job منفصل بـ CI (يعمل أسبوعيًا + على كل push/PR)، وأُضيف `.github/dependabot.yml` لفتح PRs تلقائية عند توفر تحديثات (backend، bot، Docker، GitHub Actions).
- **لا هيدرز أمان HTTP أساسية** — أُضيف `SecurityHeadersMiddleware` (`X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`) استعدادًا للوحة تحكم مستقبلية، مع توضيح صريح إن `HTTPS`/`Strict-Transport-Security` تبقى مسؤولية منصة الاستضافة.
- **الوضع الأمني كان موزّعًا عبر محادثات متعددة** — تجمّع الآن بالكامل بملف واحد صريح وصادق: **`SECURITY.md`** (يوثّق أيضًا كل نقطة أعلاه، وما زال خارج نطاق الكود مثل TLS والتشفير أثناء التخزين).

### كود ميت موثّق (Dead Code) — اكتُشف أثناء المراجعة
- **`bot/bot/keyboards.py::match_response_kb()`** — دالة مبنية بالكامل (أزرار قبول/رفض/تفاوض على تطابق شاحنة) لكن **لا يوجد أي مكان يستدعيها ولا أي handler يستقبل** `match:accept:*`/`match:reject:*`/`match:negotiate:*`. بقايا من الهيكل الأصلي قبل التعديلات؛ ميزة "عرض التطابقات بعد `/newload`" المُضافة لاحقًا استخدمت رسالة نصية بسيطة بدلها. إما احذفها، أو اربطها بـ handler حقيقي إذا احتجت تفاعل قبول/رفض فعلي على التطابقات مستقبلًا (مفيدة لو صار عندك مستخدمون فعليون على البوت، مو بس قناة الإدخال اليدوي).

## منع توقف Supabase المجاني (Keep-Alive)

Supabase على الطبقة المجانية يوقف المشروع تلقائيًا بعد **٧ أيام بدون نشاط فعلي على قاعدة البيانات**. بدل الترقية لخطة مدفوعة ($25/شهر) لحل هذا فقط، عملية البوت (شغّالة أصلًا ٢٤ ساعة) تشغّل مهمة خلفية بسيطة:

- **`GET /health/db`** بالباك-إند — استعلام حقيقي (`SELECT 1`) على Postgres، عمدًا مختلف عن `/health` العادي (اللي ما يلمس قاعدة البيانات إطلاقًا وما يمنع التوقف)
- البوت يستدعيه **كل ٣ أيام** (`bot/bot/keepalive.py`) — هامش أمان حقيقي تحت حد الـ ٧ أيام، مو ملاصق له
- فشل مؤقت بالاتصال لا يوقف البوت أبدًا — يُسجَّل باللوق ويُعاد المحاولة بالدورة التالية

**صفر بنية تحتية إضافية:** لا cron منفصل، لا منفذ مفتوح للإنترنت، لا GitHub Actions — فقط كود داخل عملية موجودة أصلًا.
